正文

我们在构建 Zed 用户界面之初面临过的挑战之一就是 Rust 严格的所有权系统。在 Rust 中，每个对象只有一个唯一的所有者，这强烈鼓励我们把 Zed 的所有数据组织成一个树形结构，且不能存在循环引用或共享所有权。在构建 Zed 之前，我大部分的 GUI 编码经验都来自 Web 技术，其中 JavaScript 的垃圾回收机制意味着你基本不需要考虑所有权。举例来说，将鼠标事件监听器附加到一个 DOM 节点上并捕获对 this 的引用，是很常见的做法，而我在构建 UI 时的直觉大多基于这种范式。在 Rust 中，在事件监听器中捕获 self 并非那么直接。

1. GPUI 为什么会引入 Entity?

2019 年 Zed 项目启动时，我们不得不重新思考我们过去在 Web 和其他框架中所学到的大部分知识和经验。我们需要一个与 Rust 相匹配的 GUI 系统，但也需要它具备渲染图形界面的动态性。例如，Zed 的工作区可以显示各种 类 型的模态对话框，而这些对话框需要能够向工作区发出事件，以指示何时应将其关闭。我们还需要异步地更新树形结构中的子树，例如在文件系统发生变化时的项目面板。当然还有许多其他示例，总之，我们希望尽量使用简单的 Rust 结构体去实现它们，而不是非常规的复杂数据结构（Exotic Data Structures）以及宏。

在尝试使用内置类型（例如 Rc ）效果不佳之后，我们开始实验一种至今仍在 Zed 的自建 UI 框架 GPUI 中使用的方法。在 GPUI 中，应用程序中的每一个 模型 或视图实际上都属于一个称为 App 的顶层对象。当你创建了一个新的模型或视图时，我们会将其统称为 Entity ，你把应用程序“状态”的所有权交给它，以使其能够参与到各种应用服务中，并与其他的 Entity 交互。

2. 如何更新 Entity 的状态？

3. Observe 机制

接下来让我们看看如何观察这些通知。在我们更新计数器之前，我们需要构造第二个计数器去观察它。每当第一个计数器改变时，我们用其计数的两倍值设置给第二个计数器。请注意，我们安排的是让第一个计数器发出通知（notify），然后在第二个计数器的 Context 上调用 observe() 来接收通知。对 observe() 的调用将返回一个 Subscription ，我们需将其 detach （译者注：这是 Subscription 一个非常典型的操作。默认情况下，一个订阅（也就是一个 Subscription 对象）应该和它的订阅者“共同生死”，也就是保持一样的生命周期，当订阅者消亡时，订阅关系也将自动解除。对于这种情形，最好的处理方式就是将 Subscription 对象设置为观察者的一个字段，例如这样： struct Counter { _subscription: Subscription } ，当 Counter 销毁时， _subscription 会一同自动销毁。也就是说：订阅关系和 Subscription 对象的生命周期默认是绑定在一起的。但是，有时候，我们并不希望这样，我们希望的是另一种情形：让订阅关系一直存在，准确地说是：维持到被订阅者（observed）销毁时，当然，如果订阅者（observer）先销毁了，订阅关系也将自动解除，如果要实现这种订阅关系，就得调用 detach() ，将订阅关系和 Subscription 对象“解绑”，也就是当 Subscription 自动销毁时，不自动解雇订阅关系）， 以便能将订阅关系维持在两个计数器都存在时。我们也可以存储此订阅并在任意时刻将其丢弃以取消此行为。

observe() 回调函数接收一个指向观察者（observer）的可变引用，以及一个指向被观察者（observed）的句柄，我们可以使用它的 read() 方法来访问其状态。

5. 如何规避“重入”问题？

现在让我们深入探讨 GPUI 的内部实现，了解 observe 与 subscribe 是如何实现的。在深入 GPUI 的事件处理细节之前，我想回忆一下我过去在 Atom 编辑器工作时的一个颇具启发性的经历，当时我在 JavaScript 中实现了一个自定义事件系统。那时我设计了一个看似简单的事件发射器，其中事件监听器被保存在一个数组中，每当事件被发出时，逐一调用每个监听器。

然而，这种简单性导致了一个微妙的 bug ，直到代码在生产环境广泛使用后才被发现。这个问题是：当一个 listener，也就是响应函数，在处理上一个事件的过程中自己又发送了一个事件（还是要由它自己处理的事件），这就是一个典型的“重入”（reentrancy）问题（译者注：“重入”（reentrancy）问题是 GUI 事件响应中的一种典型问题，它是指一个组件在执行事件响应函数的过程中，被岔开又去执行另一个（也许是同一个）事件响应函数，导致出现很多 bug 或“诡异”的行为。重入的一种最直白的后果是：死循环后导致程序栈溢出。但“重入”并不是一定会导致死循环，比如响应函数中可能存在某种条件判断，避免了死循环。“重入”实际上更侧重于强调这样一种问题：它会导致组件的“状态”不一致。这里有一个重要的“背景”，那就是：我们说，一个事件响应函数的主要工作就是根据事件来实时地更新应用程序的“状态”，比如示例中的那个 Counter，大家会默认：在响应函数的执行过程中，别处是不会在此期间修改这个 Counter 的。关于这一点，再延伸地谈一下，那就是对于 GUI 框架来说，事件响应函数通常是在单线程环境中执行的，很少会允许多线程并发执行，这跟 UI 的特殊性有关，比如 Java 的 Swing 框架采用的就是著名的“单线程队列模型”，GPUI 的处理也非常类似。所以，我们才说：在响应函数的执行过程中，别处是不会在此期间修改“状态”的。而“重入”则是在单线程情形下有可能会导致应用状态不一致的一种行为，下面代码演示了这种可能性：）

这将导致发出事件的函数在尚未执行完毕前就被再次调用。这种递归式的行为与我们对函数线性执行的预期相违背，并让我们进入了一个出乎意料的状态。即便 JavaScript 的垃圾回收器能够保证内存安全，但该语言的宽松所有权模型也让我更容易写出这样的 bug。

Rust 的约束让我们很难犯这样的错误。我们被强烈地引导着走向了另一条路径，这条路径避免了前文提到的重入问题。在 GPUI 中，当你调用 emit() 或 notify() 时，不会有任何监听器被调用。相反，我们将数据推入一个效果（Effect）队列。在每次更新结束时，我们刷新这些效果，我们会把它们从队头一一弹出直到队列清空，然后将控制权返回给事件循环。任何效果处理器本身也可以推送效果，但系统最终会进入静默状态。这为我们提供了运行到完成的语义而无需担心进入“重入”状态，并且还能与 Rust 友好地协作。下面的代码正是对这一解决方案的诠释，它来自于 GPUI 库的 app.rs ：

而 App::update_entity() 方法也没有实际处理传入的闭包，再进一步委派给了 App::update() ，实际上，在 GPUI 里所有状态的更新最终都是委派给 App::update() 去处理的，因为在这个方法里实现了 GPUI 的“防重入”机制。

App::update() 的“防重入”机制是这样实现的：在执行用户提供的 update 闭包前，先将 pending_updates 加 1 ，这是一个记录积压的更新操作的计数器，它将和开关变量 flushing_effects 一起控制更新和执行响应函数两个动作之间的“节奏”。计数器 +1 后，正式执行用户提供的 update 闭包，注意：在这个过程中，写在用户 update 闭包里的 emit() 或 notify() 就被执行了，但是，这两个方法都不会直接转去调用观察者或订阅者的响应函数，这两个方法最核心的动作是把当前发射的事件或是发出通知的实体 ID 封装成 Effect 这种数据结构，然后 push back 到 app 的 pending_effects 队列中，这是通知观察者或订阅者响应更新的“前半程”工作，然后，用户的 update 闭包执行完毕，在这个过程中不会受到中途执行的 emit() 或 notify() 的任何影响，即使需要响应这些事件或通知的还是实体自己，因为对应于它们的响应方法还没有执行，只是被 Effect 记录了下来，暂存在队列中。另外，在执行用户的 update 闭包时，还有一个很重要的情况需要清楚：那就是在执行更新期间，实体状态的所有权会临时从 App 中 lease 到了外面（这一点在下一节会看到），这是用户能在 App 外面更新状态的根本原因，在更新结束后，又会把所有权归还给 App ，这一点也保证了：更新操作只能是线性同步执行，不会出现一个 update 方法没有执行完毕，中途又插入一个 update 操作的情形，仅 Rust 的所有权机制就不允许这种情况发生，因为这意味着同一时刻将出现两个可变引用。

用户提供的 update 闭包执行完毕后，进入处理通知观察者或订阅者响应更新的“后半程”工作，也就是把此前执行 update 闭包时产生的 Effect 从队列中一一取出来，真正去执行它们，也就那些以 apply_ 开头的方法做的事情。注意：在这个过程中，响应函数是完全有可能调用 emit() 或 notify() 次发射事件或通知的，但是，这时候，程序还运行在 flush_effects() 的 loop 循环里的，新发射出来的事件或通知也是添加到队列中， loop 循环会继续 consume 这些 Effect，直到队列为空。这样，观察者或订阅者响应更新的“后半程”工作也就全部结束了。

回顾一下这个流程可以看出：GPUI “防重入”机制的核心是：发出事件后不会立即响应，而是封装成 Effect 加入到队列中，等更新操作结束后，再回过头来处理响应的问题，如果在处理响应的过程中又发出了新的事件，由于此时已完成了状态的更新，并处于“专注处理响应”的阶段（也就是 flush_effects() 的 loop 循环里），所以在响应任何事件时，实体的状态都是“一致”的。

最后，还要说明一点：执行更新的方法是 counter.update() ，负责响应的方法总是 cx.observe() 或 cx.subscribe() ，如果，我们在传给 cx.observe() 或 cx.subscribe() 的闭包里的加入一行代码，执行 counter.update() ，会不会导致“死循环”呢？这是不是“重入”呢？答案是会的，但这不是本文所说的“重入”，如前文所述，重入强调的是：在一个状态的更新尚未完成时中途又去响应另一个更新，这会导致状态的“不一致”。在我们刚列举的这个示例中，虽然程序会进入死循环，但在 GPUI 的处理机制下，每一次 update 都是在执行完毕后才进入到下一个 update 中的。当然，这已经是一个很少见的极端状态了，因为通常我们是不应该在 cx.observe() 或 cx.subscribe() 里加入 update() 方法的，这里只是回答一种可能的逻辑分支。）

6. 状态更新与租借所有权

接下来让我们使用 App::update() 实现 update_entity() 。我会在下面搭好框架，这样在继续实现之前我们可以先讨论它的签名。（译者注：此章节依然在介绍 GPUI 的内部实现机制，但谈论的已不再是上一节关注的问题，而是转向了：GPUI 是如何更新一个 entity 的状态的？这个课题涉及两个核心：一个是如何在外部获得“状态”的可变引用以完成更新操作；另一个是如何执行更新以避免“重入”问题，而这第二个问题其实在上一节已经解答了，在本节只需要在 App::update_entity() 的实现中通过调用 App::update() 去完成实际的更新就能规避“重入”问题，所以本节的重点在于解答第一个问题：如何在外部获得“状态”的可变引用以完成更新操作？）

该方法接收一个回调，该回调需要两个可变引用，一个指向待更新实体的“状态”（即： T ），第二个指向一个 Context<T> （也就是一个“视图受限”版的 App ）。由于 App 才是待更新实体的真正拥有者（进一步说也就是实体“状态”（即 T ）的拥有者），所以，这导致这个回调函数需要 T 的两个不可变引用，这是 Rust 所不允许的。

我们的变通方法是临时从 App 中“租借”实体状态，把它从上下文中移除并移动到栈上。在回调执行完毕后结束“租借”，将所有权还给上下文。

如果你在重新进入时尝试更新一个实体，这确实会带来麻烦，但在实践中我们发现避免这种情况相当容易，一旦我们出错，检测起来也非常迅速且简单。
