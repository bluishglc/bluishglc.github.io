3. 添加 GPUI 库

我们以 2.a 节创建的简单项目为基础继续后面的操作。首先就是为项目添加 GPUI 库依赖。由于 GPUI 库比较特殊，它实际上是 zed 项目中的一个 crate，并不是一个非常独立的 GUI 库，它的更新和发布实际上是跟随 zed 项目走的。这就决定了添加这个库的依赖有一些不太一样的地方，某种程度上，会更像是添加一个本地库。让我们详细梳理一下添加 GPUI 库的三种方式：

3.a 使用 crates.io 上的 GPUI 库

这个方式简单、有效。不过 GPUI 更新频繁，crates.io 上的库一般落后于 zed 项目中使用的版本。

3.b 使用 Git 上的 Zed 项目的 GPUI 库

这种方式直接从 zed 项目拉取当前最新的 zed 版本，并使用其中的 GPUI crate。这里的解释一下使用 --git 参数后的操作细节：cargo 使用 git fetch https://github.com/zed-industries/zed 命令从远程仓库下载最新的 Git 对象和引用信息，然后找到最新的一次提交，在本例中是 a50a292 ，然后，它会 git checkout a50a292 ，这样，在 %USERPROFILE%\.cargo\git\checkouts\ 下会创建一个 zed-xxxxxxxxxxxxx 文件夹，下面会有一个 a50a292 目录，存放的就是 a50a292 这个版本的 zed 项目源码 。

另外，执行上述命令后可能会报这样一个错误：

error: unexpectedly found multiple copies of crate gpui@https://github.com/zed-industries/zed at https://github.com/zed-industries/zed

这个错误可以忽略。使用 IDE 打开项目或直接执行 cargo build 是可以解析依赖并构建的。

首先， application() 方法将创建并返回一个 GPUI 应用实例，类型是 gpui::Application 。这个应用实例更多地是扮演一个应用程序“入口”的角色，它会完成一些必要的初始化工作，然后给用户留了一个 run() 方法，用户可以给这个 run() 方法传入一个 闭包 ，这个闭包其实是一个将被自动调用的“回调函数”，用户需要在这个闭包里定义应用启动后需要执行的操作，例如：打开主窗口。

通常，我们只会在应用初始化时用到一次 Application 对象，在其他大部分地方，我们会使用另一个核心对象 App ，类型是 gpui::App ，它是一个 Struct，同时实现了 gpui::AppContext 这个 Trait。GPUI 选择了集中式的所有权模型。所有应用程序状态，包括模型和视图，都由这个单一的、顶层的 App 对象拥有，同时也是用户操作应用程序的核心接口。我们来看代码：传给 run() 方法的闭包就是以 cx: &mut App 作为参数的：

它的意图是：通过调用 cx 的 open_window 方法（文档： https://docs.rs/gpui/0.2.2/gpui/struct.App.html#method.open_window ）打开一个窗口。这个 open_window 方法有两个参数，第一个参数是关于窗口的配置，如：大小、标题、是否否最大化等，在本例中为简单起见，使用了全默认设置。第二个参数又是一个闭包，这个闭包又要实现呢？GPUI 对这个闭包的要求是：必须返回一个 Entity（可以暂时理解成组件，后面会详细解释），这个 Entity 将作为这个窗口的 Root Entity (根组件），整个窗口会从这个 Root Entity 开始渲染。这里，我们简单总结一下 cx.open_window(...) 要做的事情：它将打开一个窗口，使用的是默认配置，同时它还接收了一个可以渲染的组件（ Entity<HelloWorld> ）作为窗口的根组件。应该说，这个方法的两个参数回答了全部的问题：这个窗口应该如何展示以及展示什么？

首先，外层的 cx.new() 方法（文档： https://docs.rs/gpui/0.2.2/gpui/trait.AppContext.html#tymethod.new ）专门负责将一个闭包返回的 结构体 T 包装成一个 Entity<T> [^1]，并将其纳入到 cx 的管理中。只要返回的是一个 Entity，就满足了 open_window 方法第二个参数对类型的要求。至于内层的闭包则非常简单，就是返回一个 HelloWorld 结构体实例。

run() 方法执行完毕后 GUI 应用就进入到了事件循环状态，之后的流程就由用户在界面上的操作去驱动了。回顾一下 GPUI 应用的创建流程我们会有一个鲜明的感受：GPUI 的 API 设计大量的引入了闭包，有一些函数式编程的味道。当然，这里面也有一些现实原因，比如很多闭包实际上是初始化流程中的一个回调函数，使用闭包会比较便利。

6. 核心概念 Entity

Entity 是 GPUI 中的一个非常重要的概念，它用于表示应用程序的某种“状态”（State），它可以被应用的多个不同部分共享访问，并且当状态（也就是 Entity 本身）发生变化时，应用程序的各个部分可以感知到，以便做出适当的响应。通过 Entity 可以获得跨组件的状态访问能力。下面的代码展示了如何从一个结构体创建出一个 Entity：

Entity 可以被任何实现了 AppContext trait 的类型进行管理，最常见的就是 App 对象。一般来说，我们在程序中是通过 cx.new() 来创建 Entity 的，通过这种方式创建出来的 Entity 都会被 App 持有和管理。

7. 核心概念 Render 和 View

Render 是一个 trait，只有一个 render() 方法，任何类型如果想在 UI 上将自己“展示”出来，就应该实现这个 trait。特别是对一个 Entity 来说，如果它包裹的结构体也实现了 Render，那它将既是应用程序的某种“状态”，同时这种“状态”还可以在 UI 上显示出来，此时的 Entity 就叫 View 了。

Entity 和 View 之间的“关系”：如果一个结构体被包裹成 Entity<T> 的同时，还实现了 Render trait，那么，这个 Entity 同时也是一个 View 了，但要记住 GPUI 库里没有 View 这种 trait。
