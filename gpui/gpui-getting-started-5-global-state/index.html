Rust GPUI 桌面应用开发入门：全局状态（Global 类型）

一个 GPUI 应用需要持有一些全局使用的实例或数据，它们中的大多数都是在应用启动时就创建好并存放在了 App 里一个按类型索引的 map 里：

并且，如果一个类型想要添加到这个 map 中，必须要实现 gpui::global::Global 这个 marker trait，因为用于将一个实例或数据添加进这个 map 的方法 gpui::app::App::set_global 只接受 Global 类型。所以，我们把这些要放进 App 的 globals_by_type 中去维护的实例称为：全局状态。备注：本文内容基于的是 Zed 当前（2026年10月）最新版本 v1.23.3。原文链接：https://laurence.enlightgram.com/gpui/gpui-getting-started-5-global-state/，禁止转载。

1. 全局状态的分类

一份数据或一个实例需要保存为全局状态的理由是不尽相同的，我们梳理了一些典型的分类：

1.1 服务/客户端/工具类

这是非常典型的一类实例，通常这些类型都是无状态的，在一些语言中往往会处理成单例或是由静态方法组成的 util 类。其实，这些类型中的大多数并不是真的需要成为一个单例，它们只是找不到合适的创建者或所有者。所以，Zed 让 App 扮演类似于 ServiceLocator 的角色，在需要使用它们的地方通过 cx.read_global() 或者是某个类型上的静态 global 方法（例如：SettingsStore::global(cx)）直接获取它们。此类情形的代表有：

类型 功能
db::AppDatabase 全局公用 SQLite 数据库客户端
client::GlobalClient 全局公用 Http 客户端（基于 Reqwest 封装）
fs::GlobalFs 文件操作工具类（基于 smol::fs 对文件进行异步操作）
gpui_tokio::GlobalTokio 一个 Tokio Runtime，供依赖 Tokio 的三方库使用
project::connection_manager::GlobalManager 已废弃，不再使用

1.2 全局共享状态/数据

这也是非常典型的一类情形，无需过多解释。此类情形的代表有：

类型 功能
workspace::GlobalAppState Zed 应用级核心依赖的集合，可以理解为"打开一个工作区需要的全部基础设施"
theme::GlobalTheme 当前使用中的主题
settings::settings_store::SettingsStore 应用的配置信息（加载自 settings.json）
channel::channel_store::ChannelStore Zed 协作频道（Channels）功能在客户端的数据中心
release_channel::GlobalAppVersion 当前 Zed 的版本
release_channel::GlobalAppCommitSha 这个二进制是从哪个 Git 提交构建出来的
release_channel::GlobalReleaseChannel 这是哪个发布渠道的 Zed
json_schema_store::SchemaStore 几乎不保存数据，只记录当前所有的 LspStore（弱引用），在 schema 失效时通知各个 JSON 语言服务器重新拉取
keymap_editor::KeymapEventChannel 用空 Global 做的"键位已变更"信号

workspace::GlobalAppState 可以说是所有 Global 实例中最为重要的一个，它包含了"打开一个工作区需要的全部基础设施"，它把 Arc 注册为 Global，任何持有 cx 的代码都可以通过 AppState::global(cx) 拿到语言注册表、网络客户端、文件系统、Node 运行时等共享服务，不需要一层层传参。以下是 AppState 的所有字段信息：

字段 内容
languages LanguageRegistry：所有语言定义、语法、LSP adapter
client Client：与 zed.dev 和 collab 服务器通信，内含 HttpClientWithUrl
user_store 当前登录用户、联系人等信息
workspace_store WorkspaceStore：记录所有打开的 (窗口, Workspace)，负责协作跟随等跨工作区的消息分发
fs Arc<dyn Fs>，也就是 RealFs
build_window_options 函数指针，用来生成新窗口的 WindowOptions；生产环境是 zed::build_window_options（zed.rs:359）
node_runtime Node 与 npm 管理器
session AppSession：本次会话的 id 和上次会话的 id，用于恢复工作区

而 KeymapEventChannel 非常特殊，也很有代表性，因为它是一个空的结构体，不含任何数据，所以也谈不上是共享数据，但是，它是想利用 Global 的更新通知机制，将"键位绑定刚刚重新加载过"这个信号广播给所有的观察者，让它们自动更新！

1.3 注册表

注册表其实也是一类共享数据，只是它们的“特点”更突出一些。在 Zed 的 Workspace 中有几个同类的"类型 → 构造函数"注册表，它们的机制相同：在泛型函数中把具体类型固定成函数指针，以 TypeId 或字符串为 key 存入一个 Global。

类型 功能
workspace::ProjectItemRegistry 保存文件和视图的映射关系，即哪种文件应由哪种编辑器打开
workspace::FollowableViewRegistry 协作时跟随别人，收到远端视图的 proto 描述后，在本地重建对应的视图
workspace::SerializableItemRegistry 重启时，根据数据库中的 item_kind 恢复对应的视图

2.2 基于 newtype 的 Global 类型

让原始类型直接实现 Global 的方式是最直白、易懂的，但遗憾的是，通过这种方式实现的 Global 类型并不多，更多的类型其实是单独引入了一个新的类型，让这个类型去实现 Global 特质，也就是所谓的 newtype 模式（参考《Rust 设计模式：newtype》)
举个例子就清楚了：AppState 是各处都需要的一种全局状态，但它并没有实现 Global 特质，而是另外引入一个 GlobalAppState，让它去包裹 Arc<AppState>：

Zed 为什么要这样设计呢？首先，由于 AppState 在某些场景下使用时需要获得它的所有权，所以，它基本是以 Arc<AppState> 的形式被传递和使用的，那问题其实就变成了：为什么不让 Arc<AppState> 直接实现 Global？就像下面这样：

原因是：这样编译不过！Rust 的“孤儿规则”（Orphan Rule）规定：要为某个类型实现某个 trait，trait 和类型至少有一个必须定义在当前 crate 中（这是简化后的孤儿规则描述，完整的孤儿规则请参考《Rust “一致性”和“孤儿规则”深度解读》）。Global 定义在 gpui crate，Arc 定义在标准库，gpui crate 只定义上层接口，也就是像 Global 这样的特质，各种类型如需实现 Global 应在自己的 crate 中去完成，就像 SettingsStore 那样，但是，此处的 Arc 是标准库中的类型，我们没有下手的“地方”。

“孤儿规则”的设立是为了增加程序的“一致性”（coherence），确保别人不能轻易破坏你编写的代码，同样的，你也不能随意改写别人的代码。如果没有这条规则，两个 crate 可以分别对相同类型实现相同的 trait，这会让 Rust 无法确定应该使用哪一个实现。关于孤儿规则更多的介绍，请移步《Rust “一致性”和“孤儿规则”深度解读》。

在“gpui 不适合，std 又不能写”的“两头堵”情形下，Zed 只能在 AppState 所在的 crate 中引入一个新类型，让这个新类型去包裹 Arc<AppState>。注意：新引入的类型是零成本的，不会多占用内存。实际上，这种做法在 Rust 中是很普遍的，被称为“newtype”模式，这种模式的一种典型用途就是用来克服因孤儿规则限制无法为一个目标类型实现外部 trait 这种“困境”的。

所以，总结起来只有一句话：引入 newtype 只是为了脱离“孤儿规则”（Orphan Rule）导致的无法在 Arc / Entity 包裹的原始类型上直接实现 Global 特质的困境，Zed 所有的 newtype 类型的 Global 都是因为要包裹 Arc 或 Entity 而引入的。

2.2.1 pub 的 newtype 类型

引入 newtype 后，自动获取的读写方法也是针对 newtype 而不是原始类型的，但这也不算是个大问题，取出 newtype 后，用 .0 做一个“脱壳”处理也就可以了。从这个角度上看，引入 newtype 只是多了一层包裹而已，并没有带来特别的改变。但这不是 newtype 的全部，引入 newtype 意味着多了一层“可见性”的控制层，我们认为“没有带来特别的改变”的情形是 newtype 前面有 pub 修饰，newtype 是公开可见的，例如：

属于这一情形的 Global 类型有（非完全统计，全局搜索 “pub struct Global” 可以找到全部类型）：

  • GlobalColors
  • GlobalCopilotAuth

通常这些 Global 类型不管是自身还是包裹的原始类型，都不会再额外设计 getter / setter 方法，因为它们是 pub 的，没有可见性问题，在各处都可以通过 cx.global::<Xyz>() 或 Xyz::global(cx) 获得全局唯一实例。不过，有很多类型其实并不会直接使用 getter / setter 方法，而是结合自身的属性，提供一些读取特定内容的方法，这些方法已经不是标准的 getter / setter 了，但在它们的实现中却需要使用 cx.global::<Xyz>()，这种例子特别多，比如 GlobalTheme 的 update_theme 方法。

2.3 小结

  • 要不要 newtype：看存放形式。存的是本地类型的值，就直接实现；存的是 Arc / Entity / 外部类型，就需要 newtype。

  • newtype 或 Global 类型要不要公开：看是否希望外部用 update_global 这类泛型 API 原地修改。SettingsStore 希望，所以公开；GlobalAppState 只提供读和整体替换，所以私有。
