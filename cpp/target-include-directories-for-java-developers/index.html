面向 Java 程序员的解惑：target_include_directories 到底在搞什么？

原创付费分类：C++发表于：2026-04-16阅读用时：28 分钟 (约 4230 字)阅读：0

对于从 Java 转来的程序员，在初次遇到 target_include_directories 这个指令时通常会感到非常困惑。这种困惑表现在：不知道这个命令到底在起什么作用。我认为产生这种困惑的根本原因有两点，一个是 C++ 的分离编译机制衍生出了很多在 Java 中根不存在的问题和概念，另一个是对 CMake 的运行机制了解的还不够深入。

在 Java 世界，.java 文件是整体编译的，Java 的 jar 包既是类的声明又是类的实现，在 Java 世界根本不会区分这两种概念，所以 Java 程序员也体会不到两者之间的分别，但是在 C++ 世界，代码是“分别编译”的，类的声明和定义（实现部分）是分离的，并且它们最终的存在形式也不一样（一个是文本文件，一个是二进制文件），这使得在 C++ 程序的编译过程中，会多出一条“故事线”，那就是：关于类的“声明”（也就是头文件）放在哪里？这必须要明确指出，否则代码就无法编译！

另一方面，CMake 有自己的一套包管理机制，很多 Java 程序员起初没有理解透彻，一些对 target_include_directories 非常重要的信息包括：CMake 的 install 其实和 Maven 的 install 有一些类似，它也有 Repository，只是它没有抽象出这个概念，一个项目编译发布成库，其他的项目去使用它，这中间要“共享”很多信息，其中就包括头文件的信息，而这些信息来自于源项目的 CMakeLists.txt，经过编译安装后会记录在 xxxConfig.cmake 文件中，再到使用者在项目中使用 find_package 时又会读取到这些信息，从而形成一条配置信息的“传递链条”。下面，我们会详细展开讨论一下。

1. 为什么引入一个库总得声明头文件的目录？

一个大多数 Java 程序员可能没有意识到的问题：为什么在 Java 里没有头文件？C++ 的头文件是类的“声明”，它告诉编译器一个类“长什么样”，显然，如果你想要在别处使用这个类，必须要告诉编译器这个类“长什么样”，也就是提供头文件给编译器进行参考。这是 C++ 的逻辑，非常合理，但是，在 Java 里却没有头文件，根本原因在于：

Java 不是“不需要类声明”，而是把“声明”放进了 .class 文件的元数据里。编译器在编译某个 .java 文件时，会直接读取它依赖的类的 .class 文件，从而获得这个类的“结构信息”，这就是 Java 能“没有头文件”的根本原因。

但是，在 C++ 中情形却大不相同：

C++ 编译出的库文件是关于类（包括函数、变量等）的纯二进制的机器码，不包含任何描述信息（类声明），因为在链接和运行阶段根本不需要这些信息，这些信息只在编译时需要，因此，在编译源码时，必须要提供类的“使用说明”，也就是头文件，让编译器能获得这个类的“结构信息”，这是 C++ 必须提供头文件的原因。

两相对比之下，你就该意识到： 在 C++ 中，一个完整的“库”必须包含“头文件”和“库文件”两部分 ：

  • 头文件（说明书）🠚 在编译期使用（给编译器看）

  • 库文件（机器码）🠚 在连接/运行期使用（给链接器看）

相应的，在程序里使用一个“库”也必须要同时指明库的“头文件”和“库文件”分别放在哪里 ，两者缺一不可，前者是为了：在编译时让编译器知道这个类的结构信息，以便根据类声明编译当前源码，后者是在连接和运行时真正承担工作的类的“实体”（类定义的二进制形式）。在 CMake 中设有两个专门的命令来声明 一个库的“头文件”和“库文件”： target_include_directories 和 target_link_libraries ，在 C++ 中，引入一个 第三方库 的完整操作就是得同时使用这两个命令分别把库的头文件存放目录和库文件提供出来。

回答本节标题提出的问题： 引入一个库就必须得声明头文件的目录，因为一个 C++ 的库从来都是包含头文件和库文件两部分，前者工作于编译期，后者工作于链接/运行期，引入一个库就是要分别引入头文件和库文件，让程序在编译、链接、运行的整个周期都能获取到库的相应信息 ！
