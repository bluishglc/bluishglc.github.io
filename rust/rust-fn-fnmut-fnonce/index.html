你理解的 Fn、FnMut、FnOnce 可能从一开始就错了...

原创付费分类：Rust发表于：2026-09-14阅读用时：33 分钟 (约 4888 字)阅读：0

诚如我们在 《一团乱麻？带你厘清 Rust 中的函数指针、函数项、fn 类型、Fn Trait》 中介绍过的那样，Rust 将它的函数和闭包的类型最终统一于 Fn、FnMut、FnOnce 这三个 trait 上，实现了函数和闭包的“大一统”愿景，为函数和闭包作为参数在各处传递铺平了道路。当时，我们认为故事进行到那里就已经结束了，Fn、FnMut、FnOnce 这三个 trait 虽是最后出场的关键角色，但本身却“乏善可陈”，它们各自只有一个方法，可聊的确实不多。但是，很快我们就会在实际编程中意识到问题：我们对于 Fn、FnMut、FnOnce 的认识过于肤浅，甚至出现了很大的偏差。一个典型的例子就是：当我们第一次看到一个函数的类型约束是 F：FnOnce() -> T 时往往会认为这是一个很严格的约束，因为它只接受一次性闭包，然而实际上，它却是最宽松的约束，所有的函数和闭包，只要参数和返回值的数量和类型得匹配上，都可以传入。绝大多数的 Rust 初学者都会对 Fn、FnMut、FnOnce 这三个 trait 产生极大的误解，这是由多种因素叠加造成的，里面有很多“故事”，远不是三个“单薄”的 trait 那样简单。本文原文链接 https://laurence.enlightgram.com/rust/rust-fn-fnmut-fnonce/ 禁止转载！

1. 函数与 闭包 的“类型”

我们知道，对于一个函数（包括函数指针和函数项两种指代形式）或闭包来说，它们都有自己专属的类型，其中函数项和闭包的类型是编译器根据它们的定义自动生成的，但是，这些自动生成的类型都是“匿名”的，你无法写出或使用它们，不过，Rust 在生成它们的类型时会根据函数和闭包的情况，自动为其实现 Fn / FnMut / FnOnce 这三个 trait 中的一个，这样，我们就可以用这三个 trait 作为函数或闭包的类型描述了，下图来自 《一团乱麻？带你厘清 Rust 中的函数指针、函数项、fn 类型、Fn Trait》 ，它准确描述了 Fn / FnMut / FnOnce 和函数与闭包之间的关系：

可以说，经过层层处理和抽象之后，在 Rust 中，函数和闭包的类型最终统一在了 Fn / FnMut / FnOnce 这三个 trait 上，函数和闭包可以类型化后，就可以作为参数传递给另一个函数，这是意义重大的一步。

2. Fn、FnMut、FnOnce 之间的关系

人们容易错误地把 Fn、FnMut、FnOnce 看成是三个独立的 trait，一个闭包可能会选择同时实现一个、两个或三个，这是不正确的。 一个函数或闭包，只会被编译器自动实现为其中的一种，而不是同时实现一种、两种或三种 ！只不过，因为 Fn 继承（叠加）了 FnMut、FnOnce，所以在实现 Fn 时必然实现了 FnMut、FnOnce 规定的部分，同理，FnMut 继承（叠加）了 FnOnce，所以在实现 FnMut 时也必然实现了 FnOnce 规定的部分。“只会实现其中一种”和“同时实现一种、两种或三种”这两种表述有什么区别吗？有！ 后者极容易让人错误地将 Fn、FnMut、FnOnce 理解成三个完全独立的 trait，而忽略了三者其实是继承（叠加）关系 ！下图展示函数/闭包和三个 trait 之间的真实关系：

3. “反直觉”的约束关系

Fn、FnMut、FnOnce 有一个特别容易把人搞晕的地方，通常，我们会下意识地认为：一个函数，或者一个既不依赖外部可变引用又不消耗外部值的普通闭包才是最常见的情形；如果一个闭包依赖到了外部可变引用，人们就会认为这是比较特殊的状况了；而如果一个闭包还要消耗掉外部的值，那就是更为少见的特殊情况了，所以，人们会下意识地给 Fn、FnMut、FnOnce 这三种 trait 进行排序，认为 Fn 是最常见、最通用的情形，FnOnce 是最少见、最特殊的。

基于这样的一种感官印象，当人们第一次遇到 F：Fn() -> T 这样的类型约束时，会自然地认为这是宽松的类型要求，函数以及三种不同形式的闭包都可以传入，而看到 F：FnOnce() -> T 时则会认为这是最严格的约束，只有最特殊的一次性闭包可以传入，于是认为： F：FnOnce() -> T 是比 F：Fn() -> T 更严格的约束。很糟糕的理解，因为完全搞反了！实际上，是 F：FnOnce() -> T 可以接受任何形式的函数和闭包，它是最宽松的，而 F：Fn() -> T 只能接受函数和无自由变量或仅含只读自由变量的闭包，它是最严格的 。这是 Fn、FnMut、FnOnce 三个 trait 最反直觉的地方，我们可以死记硬背下正确的排序，但这解答不了我们心中的疑惑：为什么会搞反呢？我们必须把这个问题分析透彻，这需要回到一开始的认识，重新梳理。

“Fn 最常见，FnOnce 最少见”这个主观感受没错，也符合概率统计，我们在阅读和编写代码时，遇到的所有函数以及绝大多数的闭包都是 Fn 类型，FnMut 和 FnOnce 类型的闭包很少见。但是，这里我们犯了一个不易察觉的错误： 最常见 ≠ 最通用，最少见 ≠ 最特殊，我们把类型在继承关系中表现出的“通用性”（即：基于父类编写的代码通用性更好，可以无缝代入所有子类执行）和它们在代码中的使用频率混为了一谈 。

实际上，我相信很多人知道 Fn、FnMut、FnOnce 三个 trait 的继承关系是 Fn: FnMut: FnOnce ，但还是会义无反顾地将它们的关系搞反。根据三者的继承关系，FnOnce 位于继承关系的顶端，它才是最通用的，Fn 位于继承关系的末端，它才是最特殊的。 基类 = 通用 = 宽松约束，子类 = 特殊 = 严苛约束 ，这条 OOP 的铁律同样适用于 trait 的继承关系（尽管 Rust 里是没有基于类的继承关系，但是 trait 是有继承关系的，并且遵循相同的继承规律）。下图是遵循 Fn、FnMut、FnOnce 继承关系绘制的它们本来的通用性和约束性描述：
