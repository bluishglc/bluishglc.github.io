1. Logging 与 Tracing

花开两朵，各表一枝，咱们先解释一下什么是 logging 什么又是 tracing。logging 都很熟悉了，不需要解释，不过大家需要知道一点 Rust 日志库生态的历史，早期，Rust 官方定义了标准的日志库：log (https://crates.io/crates/log)，但这只是一个 logging facade，也就是只定义了 Rust 官方的 logging API，并没有提供具体实现，而是把这个工作留给了社区。这些年，Rust 也涌现了一些不错的日志库，具体可以参考 Rust 的官方推荐：
https://github.com/rust-lang/log#in-executables ，一些比较常用的三方实现库是：env_logger、simplelog 等。它们和 log 之间的关系和 Java 中 log4j、logback 与 slf4j-api 之间的关系是一样的。

接下来，介绍一下 tracing。在大型 分布式 系统中，例如使用微服务架构的大型 Web 应用，一条用户请求可能会横跨多个独立部署的服务，此时再用传统的日志方式去跟踪这条用户请求就变得非常困难，这就是为什么要引入分布式追踪框架的原因。分布式追踪的核心思路是：在请求的开始生成一个 trace id，然后将该 trace id 一直往后传，请求经过的每个服务都会使用该 trace_id 记录相关信息，最终将整个请求的链路串联起来。

Tokio 是 Rust 最主流的异步运行时，由于在多线程环境下，传统的日志系统无法很好地反应程序真实的调用情况，这和分布式系统中面临的问题是类似的（虽然场景不一样，但需求是一致的），所以它提供了一个子模块：tokio-rs/tracing（https://github.com/tokio-rs/tracing），这是一个不依赖 Tokio 可以独立使用的 tracing 框架，严格来说，tokio-rs/tracing 并不是一个日志库，而是一个分布式跟踪的 SDK，用于采集监控数据的，但是在涉及到记录追踪信息部分的功能时， tokio-rs/tracing 主动适配了 Rust 的 log 门面库，这就使得它既可以作为分布式追踪的 SDK 来使用，又可以作为独立的日志库来使用 。

这几年，Rust 生态的日志系统已经普遍从过去的 log + env_logger / simplelog 体系过渡到了 tokio-rs/tracing。诚如前面所介绍的，后者能更好地记录和追踪分布式和多线程环境下程序的运行状况，这是 tracing 库变得越来越主流的根本原因。

2. Tracing 基本概念

tokio-rs/tracing 定义了三个核心概念，它们构成了 tracing 的核心：

  • Spans：定义了一个有开始和结束的时间段，用于跟踪程序的执行流程

  • Events：就是传统的日志消息，但它总是与 span 相关联

  • Subscribers: 订阅日志并以自定义的过滤规则和格式进行输出

下图展示了 Subscriber、Span、Event 三者之间的关系：

tracing 框架包含多个常用组件，它们有：

  • tracing: 提供 tracing 框架的基础功能，写代码会用到的 event，span, instrument 都在这个包里

  • tracing_subscriber: Subcriber 就是日志的收集方，发负责接收 Event、Span 并过滤、格式化并输出消息

  • tracing_appender: 负责将日志写入文件

  • tracing_error: 增强记录错误发生时的上下文

  • tracing_log​: 用于桥接标日志准库和 tracing（将 tracing 适配到官方 log API）

6. 理解并使用 Span

从使用方式上来说，可以说，tracing 区别于普通日志框架最大的地方就在于它可以定义 Span 了。 Span ( https://docs.rs/tracing/latest/tracing/span/index.html ) 负责记录事件发生的地点和上下文信息，如果作用域内没有 Event 发生， Span 不会输出任何信息。如果作用域内有 Event 发生，在输出 Event 信息的同时，也会将进入的 Span 信息从近到远依次输出，携带相关的上下文信息。下图展示了一个完整的日志流程，我们可以从中看到 Span 发挥的作用。在初始化一个 Subscriber 后，大量的日志都是在一个“上下文”中产生的，也就是关联到一个 Span 上，具体的做法就是：先创建一个 Span，然后进入这个 Span，此时产生的日志都自动关联到这个 Span 上的，只到程序从当前 Span 退出，这个上下文就算结束了。然后现开启一个新的 Span，当然，Span 之间也可以形成嵌套关系。

  4. 创建和进入 span 往往可以二步并作一步执行，直接使用 entered() 方法即可

  5. 由于在离开作用域时，守卫对象 _enter 会被自动释放， span 会自动关闭并清理。所以，我们几乎不需要手动退出一个 span。如果在特殊情况下需要手动提前退出，可以使用 drop 方法

  6. 以上关于 span 的种种操作，理论上，都应该是通过 span 对象来调用的，但是，你会发现，我们除了通过 span 对象创建过一个守卫对象外，再也没有显式地使用过它，并且，还有一个更应该值得我们好奇的地方：为什么进入 span 之后，与 span 并没无直接瓜葛的 event!() 能把自己消息绑定到当前的 span 中呢？原因很简单，真正的 span 对象其实是一个 thread local (线程局部变量）。

6.4 理解并使用 Span 的 Fields

我们在前面的几个示例中已经见到过 Span 的 fields 了，例如 example_5.rs 中出现的 user_id = 1000 和 example_6.rs 中出现的 service = "order" ，对于只使用过日志框架没使用过追踪框架的人来说会有一个困惑：在 Span 里设置的自定义键值对（也就是 fields）有什么用呢？其实它的应用场景非常典型，因为：Span 代表着一种上下文，在程序中会有一些变量或数据是绑定在上下文中的，典型的例子有用户请求携带的 request_id，数据库查询时携带的 SQL 语句。在 Span 中记录这些字段就能通过这些字段和对应的值快速索引、过滤、聚合和关联相关的日志信息，而不必从日志文本中进行字符串解析。一个容易被控制台输出的日志信息所误导的是：Span 的 Fields 是以真字段的形式存在于结构化的数据载体中的，这一点在使用 json 保存日志信息时就能体现出来，而在控制台上展示时，看出来消息的结构。这就是为什么能通过字段和对应的值进行检索和过滤的关键原因。

不过，大多数情况下，我们不会像 example_5.rs 中出现的 user_id = 1000 那样去 Hard-Code 一个 Field 的值，因为，这个值一则是在定义时还无法确定，二则是是它可能会不断变化，所以，通常我们会使用 user_id = field::Empty 这样的方式去先声明一个空的 Field，然后在后面的代码中再通过 span.record() 去设置运行时获取到的实际值。下面的例子演示了 Field 的动态设置和使用：
