一个 Rust 多线程的笼统问题：一个值和它的引用交叉分布于不同线程中可以有多少种情况？哪些是合法的？

这是在研究 Send trait 时衍生出来的一个支线问题。我们说一个值跨线程 move 之所以会有线程安全问题（本文我们特指数据竞争问题）一定是有什么数据在 move 后会出现既被读又被写的情况，或者说本来这种数据就是既被读又被写的，只是在单线程环境下被人们忽略了，那会是什么数据呢？我们首先怀疑的就是值本身，但是，这个怀疑其实很容易排除，问题描述的是值的 move，move 只会改变所有权（由编译器记录下谁（哪个变量（绑定））将负责最后销毁值），不会修改任何数据。这里可能有人会担心：也许是 move 后，在新线程中又创建了不可变或可变引用呢，然后和再原线程中的引用一起来竞争值呢？这可能是很多人担心过，但又未必能清晰描述出来的场景，这里其实有好多臆想出来的假设，但实际上它们根本没法编译通过，本文我们就深入分析一下这个假设性问题。首先，这个问题可以重新表述为：

在多线程环境中，一个值和它的引用可能会分布在多个线程中，从代码层面看（编译期），值和引用是分布于不同的闭包中，有确定的先后顺序（定义顺序）；从执行层面看（运行期），值和引用分布于不同的线程中，无确定的读写顺序（是指线程间的，不是线程内的），笼统地看，这就形成了值与引用在编译期交叉分布于不同的线程中（实为 spawn 闭包），在运行期更是交叉分布于不同线程中且无确定顺序的复杂情形，那这些交叉组合一共有多少种情形，哪些情形是合法或线程安全的，那些又是非法或线程不安全的呢？

这中一个很笼统的问题，可能提问者脑子里还没有形成一个关于 Rust 多线程合理的 知识图谱 ，但是这个问题的出发点是很朴素的，值得思考并记录下来。这个问题看上去很复杂，如果真得一一列举的话就“跑偏”了，我们应该先分成编译期和运行期两类情形分别研究，因为编译期不合法的情形就没必要再拿到运行期去分析了。

1. 编译期：值和引用跨线程（实为跨 spawn 闭包 ）交叉分布的研究

首先，我们得先清晰地明白一点： 虽然从逻辑上可以说：值与引用交叉分布于不同的线程中，但是，Rust 编译器并没有线程概念，它只是单纯地分析值、引用、所有权和借用规则，与是不是多线程环境毫无关系，唯一一点“特殊状况”就是每一个线程中的代码是在一个由闭包建立的独立作用域中，仅此而已 。基于这个重要的认识，很多情形都可以被所有权和借用规则直接排除！ 注意：本文我们是想站在一个“初始的简单视野”来思考这个问题的，所以只讨论 thread::spawn() 和普通的类型，不讨论 thread::scope() 和 Arc ，因为它们确实会打破我们下面讨论的规则 。

基于上述分析， 这个问题其实已经“退化”为：一个值和它的引用在普通代码中可以有几种形式的分布？这个问题的答案就是借用规则本身，只不过由于 spawn 总是要求必须把依赖到的值 move 进闭包中，所以无非是中途会出现所有权转移这种情形 。我们还是得通过一些示例来分析一下。

2. 运行期：值和引用跨线程交叉分布的研究

通过了编译期的所有权和借用检查之后，进入到运行期之后，还有哪些值与引用交叉分布于不同线程（spawn 闭包）内的场景吗？答案是：没有了（事前已排除了 thread::scope() 和 Arc），同样的，也是找不到反例了。有一些吃惊对吧？也就是说： 我们预想的几乎所有非法的值与引用交叉分布于不同线程中的情形，几乎都在编译期被所有权和借用检查“毙”掉了 。

3. 编译期（补充说明）：强制使用 move 闭包极大减少了值与引用交叉分布的可能情形

第 1 节，我们对编译期能通过所有权和借用检查“毙”掉几乎所有非法的值与引用交叉分布于不同线程中的情形的总结并不完善，这并非全部是所有权和借用规则的功劳，这里面还有一个很重要的限制堵死了一部分原本可能会发生的错误情形，那就是： thread::spawn() 总是要求它的闭包必须把依赖到的值 move 进闭包，这是通过给闭包的类型添加 'static 约束实现的，这个约束极大的收窄了值与引用交叉分布的可能情形 ，因为值一旦被移动到闭包内，就意味着在闭包出现的位置之后（也就是其他线程的定义中），不能再出现值的引用了（注意，这是从定义顺序（编译期）上下的结论），而如果是闭包出现之前的位置上有引用，只能是已执行完的代码（例如 case 1 主线程与子线程 那样，最后一次使用是在 move 前，这不违反借用规则），还有一种可能是和当前闭包并行执行，那就是 case 2 两个子线程那种情形，但这种情形已经被所有权检查“毙”掉了。
