1. 循环引用是如何发生的？

当我们使用共享指针时，是很容易发生循环依赖的：只要两种数据结构相互持有对方的共享指针就很容易形成循环依赖，导致两种数据结构在释放时相互依赖对方先释放，致使强引用计数始终无法归零。我们还是通过示例来看一下吧。继续使用我们在 《Rust 语言特性：智能指针 Box＜T＞》 和 《Rust 语言特性：共享指针 Rc＜T＞》 中使用过的 cons list 结构，看下面这样一个示例：

我们简单分析一下 a 和 b 强引用计数的变化过程：最初，在第 2 行创建 a 时，只有 a 自己这一个 位于栈上的 Rc 指针，此时它的强引用计数是 1，至第 7 行时，在创建 b 的过程中需要将其尾元素设为 a ，故使用了一次 Rc::clone(&a) ， a 的强引用计数变为 2， b 刚创建，此时它的强引用计数还是 1，进行至第 14 行时，我们把 a 的尾元素替换成了 b ，这时需要调用一次 Rc::clone(&b) ， b 的强引用计数变也为了 2，且 a 和 b 形成了循环依赖。

如果注释掉最后一行的打印语句，不让程序报错，则实际上， a 和 b 将永远无法释放，这已经是一种内存泄漏了。为什么这样的说呢？按照局部变量按逆序销毁的规则，当 a 和 b 离开作用域时，会先尝试销毁 b ， b 的 drop 函数会被自动调用，且正常情况下，还会级联调用它所有成员的 drop 函数，也就是 drop glue，但是，对于 Rc 类 型来说，它的 drop 函数逻辑是：先让强引用计数减 1，然后判断是不是已经为 0，只有变成了 0 才会继续释放它指向的共享数据，以及级联调用它的成员字段的 drop 函数，对于 b 来说，这些都没有发生，也就是： b 指向的位于堆上的 List 数据没有被清理， a 的 drop 函数也没有被级联调用，整个过程只有位于栈上的 b 指针被销毁了。

同样的情形紧接着发生在了 a 身上，在执行 a 的 drop 函数时， a 的强引用计数从 2 减到 1，由于也不是 0，所以， a 指向的位于堆上的 List 数据没有被清理， b 的 drop 函数也没有被级联调用，整个过程只有位于栈上的 a 指针被销毁了。这样， 最后，位于堆上的 a 和 b 两个指针指向的共享数据都错过了最后的清理机会，它们内部的强引用计数都是 1，且在栈上也没有任何再指向它们的 Rc 指针，这就意味着，它们再也没有了“名字”（失去了地址），成为了内存里的“黑户”，它们所占用的内存就实质上被“泄漏”了 。

3. Weak 的典型应用场景

不过，上面的例子并不是展示 Weak<T> 最好的例子，因为 a 和 b 形成的循环依赖是我们人为设置的，并不符合它们的自然关系。通常，介绍 Weak<T> 会使用树形结构作为例子，因为 在树形结构中，父节点拥有子节点，而子节点不拥有但可以持有对父节点的“依赖”，这种关系是组合使用 Rc<T> 和 Weak<T> 形成双向关联关系的同时又不会出现循环依赖的典型场景 。下面我们就详细了解一下。
