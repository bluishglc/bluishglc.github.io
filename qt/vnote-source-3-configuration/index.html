原创付费分类：Qt发表于：2026-04-14阅读用时：19 分钟 (约 2807 字)阅读：0

VNote 的配置系统是程序运行的基础，各个模块都会使用到配置类来读写应用和用户的配置。不过，VNote 在配置这一块实现很繁琐，有很多逻辑也很别扭，突出表现为：抽象层级不清 + 数据冗余，个人猜测应该是在历史演进过程中积累了一些技术债务，使得这一部分的实现很不“清爽”，本文会解读一下这部分内容。

1. 配置分 类

配置分类有两种维度：按文件分、按功能分，两种维度又会有交叉，同一功能对应的配置在 default\ app \user都有有可能存在！

1.1. 按作用层级分

配置类型 文件路径 说明
Source::Default :/vnotex/data/core/vnotex.json 应用的资源文件，嵌入在 exe 文件中
Source::App C:/Users/<USER>/AppData/Roaming/VNote/VNote/vnotex.json 初次运行时是从应用程序中（ :/vnotex/data/core/vnotex.json ）复制而来，Default 和 App 对应的配置完全一致，且是只读的，App 这层配置极为“迷惑”，基本没有作用，可能唯一的作用是给用户作为模板参考用的
Source::User C:/Users/<USER>/AppData/Local/VNote/VNote/vnotex.json User 的配置是同时读取 User + App 的配置然后按字段 merge，最后整体写回到 User 中（参考IConfig::readString方法）
Source::Session C:/Users/<USER>/AppData/Local/VNote/VNote/session.json 初始为空，后完全由程序写入

从逻辑上说：一个配置项的最终值是依次按 User 🠚 App 🠚 Default 顺序查找的（ Session 是在自己独立的赛道中），先在哪里找到就以哪里为准，也就是说 User 有最高优先级，然后是 App，最后是 Default，但是，这只是逻辑上的，VNote 的实现其实很不优雅，甚至让人“迷惑”，实际的情形是这样的：

App ≈ Default ：App 的配置文件是直接复制了 Default，且程序几乎不会改写 App 的配置（连文件都是只读的）
User ≈ 最终配置 ：既然 App 几乎是静态的，所以实际上用户配置的信息只保存在 User 中，而且 User 配置文件中的初始信息也是从 App 中 by 配置项 merge 过来的
