解读 Qt “对象树”和“界面结构树”的底层逻辑

原创付费分类：Qt发表于：2026-03-02阅读用时：17 分钟 (约 2599 字)阅读：0

刚开始尝试编写 Qt 代码时，我们会遇到这样一 类 问题：创建好了一个 menu，也把 parent 设为了 menuBar 但却显示不出来；创建好了一个 action，也把 parent 设为了 menu 也显示不出来，后来发现还必须调用 QMenuBar::addMenu() 把新建的 menu 添加给 menuBar 以及调用 QMenu::addAction() 把新建的 action 添加给 menu 才能在界面上看到它们。于是，这就引出了我们的问题：为什么设置了 parent 却没有实现我们想要的“添加”效果，还要再另外调用 add 方法？现然两个方法肯定做了不一样的事，在 Qt 里是怎么定义：“子设置父”和“父添加子”这两种行为的？是否分别赋予了不同的含义？这个问题涉及到的 Qt 中的两个重要概念，一个是“对象树”，另一个没有一致的称谓，本文使用“界面结构树”指代，后文会详细解释。

在我们展开讨论前，我觉得有必要给有经验的程序员提一个醒：我们知道，在所有具有层级关系的数据结构中，关联“父子关系”都有两个独立动作：1) 子对象设置 parent；2) 父对象添加 child，一套数据结构的设计者可以选择在“子对象设置 parent 时同步调用 parent 的 addChild() 方法完成双向关联”，也可以选择在“父对象添加 child 时同步调用 child 的 setParent() 方法完成双向关联”，或者什么都不做，让用户自己维护是否需要建立双向关联关系。

但是，在 Qt 里情况完全不同，Qt 的所有控件确实都有 setParent() 方法，部分的容器型控件和布局也有 addXxx() 方法，但是这两套方法和树形数据结构中所谓的“建立父子双向关联”不能说没有一点关系没有，但关系确实不大。 笼统地说：Qt 依靠设置父控件（setParent() 方法）建立“对象树”，依靠添加子控件（addXxx() 方法）建立“界面结构树” ，这是两条相对独立的逻辑线但在一些地方又会有交叉，比如：在某些容器型控件添加子控件时会自动调用 setParent() 方法把子控件的 parent 设为自己，而 Layout 和另外一些容器型控件（如 QButtonGroup）则不会，再比如有的控件仅需 setParent 即可，而有的需要在 setParent 的同时还要其父控件主动 add 它，否则控件将不可见。所有这些情形，我们都会在本文逐一讨论。

1. 明确概念

1.1 界面结构树

UI 界面上各种控件因布局（自上到下的排布关系）会天然地形成一种“树形结构”，这种“树型结构”是一种 视觉 上的，逻辑上的，虽然 Qt 官方没有给这种树形结构起一个专属名称，但它是“确确实实”存在的，主要体现在“我们需要显式地调用某种 add 方法将视觉上（逻辑上）具有上下级关系的布局、控件装配在一起”，具体到代码层面就是指容器类控件和布局的 addXxx() 子控件方法，例如： QLayout::addWidget() 、 QMenuBar::addMenu() 、 QMenu::addAction() 等。由于没有找到一种广泛使用的称谓，本文我们暂且把这种树形结构称为“界面结构树”。在 《手把手带你写 Qt 应用主窗体》 一文中，我们绘制了一个典型窗体应用的界面结构树，这里引用一下作为一个示例：
