Flink CDC 与 Kafka 集成：Snapshot 还是 Changelog？Upsert Kafka 还是 Kafka？

原创付费分类：Flink发表于：2024-02-05阅读用时：21 分钟 (约 3148 字)阅读：0

我们知道，尽管 Flink CDC 可以越过 Kafka，将关系型数据库中的数据表直接“映射”成数据湖上的一张表（例如 Hudi 等）， 但从整体 架构 上考虑，维护一个 Kafka 集群作为数据接入的统一管道是非常必要的，这会带来很多收益。

在 Flink CDC 之前，以 Debezium + Kafka Connect 为代表的技术组合都是将数据库的CDC数据先接入到 Kafka 中，然后再由后续的组件解析和处理。引入 Flink CDC 后，我们同样可以沿用这种架构，对于 Flink CDC 来说，这只不过是将原来某种格式的 Sink 表改成了以 Kafka 为 Connector 的 Sink 表，改动及其微小。同时，Flink CDC 本身的架构和使用方式要比 Debezium + Kafka Connect 方案简单地多得多（后者需要专门的 Kafka Connect 集群），所以，使用 Flink CDC 将关系数据的 CDC 数据接入到 Kafka 这一方案，是非常不错的一种技术选型。

本文，我们会围绕这一主题，专门研究与之有关的两个 Connector：kafka / upsert-kafka 和两种 Foramt： json / debezium-json 之间的四种组合，通过四个测试来阐述：kafka 和 upsert-kafka 两种 connector 之间的区别，以及 debezium-json 这种格式和普通 json 格式的区别又是什么。在详细展开前，我们先将重要结论梳理如下：

这里再巩固一下动态表的概念，以防止错误解读。我们下面的四组测试在 Kafka 上创建的四张表都是 “动态表”， 动态表（流）的输入必是 changelog 数据（即使你供给的数据可能不是 CDC 那样的 changelog 数据，就是 append-only 数据，Flink 也依然是按 changelog 方式解读），输出也必是 changelog，至于 changelog 是什么格式，怎样解析，这由具体的 connector 和 format 来定义，就像在 connector=kafka，format=debezium-json 和 connector=upsert-kafka，format=json 这两种方案中的 changelog 格式和组织形式都不一样，但它们作为 changelog 的固有属性是不变的， 动态表的“当前状态”维持在内存中（即Table 视图所显示的）！当动态表作为 sink 被持久化到存储介质中或传递给下游时，也是以 changelog 形式存储或传输的 。

那这里有一个关键问题：既然前两个方案都能在 Kafka 上"复刻"出数据库中的一张数据表，并保持实时更新，那它们的区别是什么？这个问题其实还有点 tricky, 目前看，它们确实是没有本质差别，前者是借助格式（debezium-json）来记录数据变更的，用直白的方式读取 kafka 消息即可；后者是借助对消息的一些“约定”来实现的，功夫是放在 connector 的实现上了，这样解放了消息表格本身（使用通用数据格式就可以）！不过，upsert-kafka 方式因为数据结构更简单，理论上解析处理起来会更快捷一些，至于是否有深刻或本质的差异，有待后续思考和补充 ！

2024/3/15 补充：抛开使用的 format 不谈，upsert-kafa 和 kafka 两种 connector 的区别有点类似于 mysql-cdc 和 jdbc 两种 connector 的区别。简单地说，upsert-kafa 就是在 Kafka 上构建一张 Flink 动态表的原生解决方案（不借助特殊格式，可记录和反向解析changlog)

upsert-kafka（作为 Sink 时）是将一张动态表物化到 Kafka 上的解决方案，物化时它必须能记录动态表的变更历史（changelog）；反之，作为 Source 时）它能从 Kafka 上恢复出一张动态表，同样能根据新输入的 changelog 数据动态变化。
