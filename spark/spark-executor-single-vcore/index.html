为什么我的 Spark Executor / Yarn Container 只有一个vCore?

原创付费分类：Spark发表于：2023-08-17阅读用时：11 分钟 (约 1578 字)阅读：0

在很多集群里，在关闭了Spark的DynamicAllocation的前提下（避免自动申请空闲资源，干扰测试结果），都会观察到：提交Spark作业时，申请 1 个 driver + n 个 executor 会在Yarn上对应创建 n+1 个 container，但是每个container只有一个vCore，通过 --driver-cores 和 --executor-cores 设定的vCore数都未奏效。有人会因此错误的认为Yarn上的一个vCore对应一个Spark的executor，这是非常错误的，正确的关系是： 一个Saprk Executor运行在一个Yarn Container里，Executor和Container是一对一的关系。Executor申请的vCore就是Container的vCore ，但后半句其实是有条件的，上面描述的就是一种例外。

实际上，上面说的：一个 spark executor / yarn container 只分配一个vCore其实挺常见的，因为这种现象和一个 配置项 有关，在这个配置项的默认配置下，集群的行为就是这个样子，所以这种情况出现的概率很大。下面就详细介绍一下导致这种情况发生的原因和修正方法。

1. 重要结论

在使用Capacity Scheduler的前提下，Yarn有一个配置项： yarn.scheduler.capacity.resource-calculator ，它是用来指定使用哪种方法(策略）计算集群资源的，这将决定资源调度器如何为一个作业分配内存和CPU。该配置的默认值是： DefaultResourceCalculator ，它的特点是： 在资源分配时只考虑内存（不考虑CPU） ，那这会引发一个问题：如果只是按内存分配资源，那CPU资源将怎么分配呢？从目前表现出的行为来看，DefaultResourceCalculator 对于CPU资源的切分方法就是： 一个Container总是固定分配一个vCore 。这一点和文章开始描述的状况是完全一致的。

怎么看待 DefaultResourceCalculator 这种行为逻辑呢？应该说，它还是有合理性的，它的设计初衷应该是这样的：让一个Container总是固定分配一个vCore并没有大的问题，因为并行度完全只以由Container的数量来控制，这样，用户只须操心内存的分配即可，更准确地说应该是：用户只需要考虑在1个vCore的Container里分配多少内存即可，这样，整体的资源分配其实是由Container数量（即vCore的数量）和每个Container分配的内存来决定。 DefaultResourceCalculator 的这种设计思路其实就是将内存和CPU两种维度的资源“降维”成内存这一种维度（vCore固化为1）去切分，初衷应该是简化资源切分的复杂逻辑。

然而，Spark的 --driver-cores 和 --executor-cores 设计显然和Yarn 的 DefaultResourceCalculator 逻辑是不兼容的，既然Spark是运行在Yarn上，所以最终的资源分配还是Yarn来决定的。所以，用户看到的状况就是：无论它们给 --driver-cores 和 --executor-cores 配置什么样的值，driver 和 executor 对应的Container实际分得的vCore 总是 1， 这就是问题的根源了。

解决方法其实是很简单的，就是“换种同时考虑内存和CPU资源”的切分方法即可，在Yarn上，这种方法是DominantResourceCalculator。

DominantResourceCalculator 在资源分配时会综合考虑内存和CPU ，通俗地说，它符合人们的普遍认知，即： 我可以为我的Container分配明确的内存和CPU（而不是只能指定内存，让CPU固化为1vCore） 。很显然，DominantResourceCalculator的分配逻辑和Spark的 --driver-cores 和 --executor-cores 是可以匹配的，所以，在DominantResourceCalculator模式下，这两个参数设定的值才会起作用，也就是能反应到Container上，下面我们看两个测试用例就清楚了。

关于 DominantResourceCalculator 的更多介绍，可以参考 https://docs.cloudera.com/HDPDocuments/HDP2/HDP-2.6.1/bk_yarn-resource-management/content/about_yarn_resource_allocation.html
