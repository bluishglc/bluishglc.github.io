在已能把整库同步到 Kafka 的基础上，作者调研了后半程：读取 Kafka 中的 Debezium CDC 数据写入 Hudi 表，并要求整库或多表在一个作业中完成。作者优先调研了 Hudi 内置的 HoodieMultiTableStreamer。文章指出链路中的两个技术要点：HoodieStreamer 强依赖 Schema Registry，而 Flink CDC 的 API 写入 Kafka 时无法自动注册 Schema，只能通过 Rest API 手动注册。最终结论是单表可行，但多表在 Hudi 多个版本 上均测试未通过，基本可确定是其 Bug。

Hudi HoodieStreamer 报错 DebeziumSource only support SchemaRegistryProvider 解决方法

HoodieStreamer 摄取 Debezium 消息时可能报 DebeziumSource only support SchemaRegistryProvider。解决方法是配置 SchemaRegistryProvider 并搭建 Schema Registry。作者进一步分析了它对整条 CDC 链路的影响：上游写入 Kafka 时也必须注册 Schema，而 Flink CDC 的 API 并不支持。因此只能二选一：用 Kafka Connect 加 HoodieStreamer，但无法整库同步；或去掉 Schema Registry，用 Flink CDC 整库摄取后自行分流。

Flink CDC 提取记录变更时间作为事件时间和 Hudi 表的 precombine.field 以及1970-01-01 取值问题

原创分类：Hudi发表于：2024-02-27阅读用时：8 分钟 (约 1135 字)阅读：0
CDC 数据中的记录变更时间是天然的事件时间，也是 Hudi 表 precombine.field 的最佳选择。本文以 Flink CDC 的 MySQL 连接器为例，介绍它提供的四种元数据，说明如何在源表中声明类型为 TIMESTAMP_LTZ(3) 的 op_ts 列来提取变更时间。初次使用时会发现写入的值全是 1970-01-01，这是有意设计：默认的 initial 模式先快照读取历史数据，此时没有变更时间，op_ts 取 0，只有从 binlog 读取的增量数据才有真实时间。这对 Hudi 表没有影响，还能顺便区分记录来自全量还是增量。

问题：Spark SQL 读不到 Flink 写入 Hudi 表的新数据，打开新 Session 才可见

原创付费分类：Hudi发表于：2024-02-21阅读用时：3 分钟 (约 426 字)阅读：0
用 Flink 向 Hudi 表写入数据，再用 Spark SQL Shell 查询时，可能只能看到打开 Shell 之前的数据，新开一个 Session 才可见。这并不是 Bug：Spark SQL 的 Session 会缓存表和文件的元数据，而 Flink 对 Hudi 表的写入不在 Spark 的感知范围内，导致其继续使用过期的元数据。解决方法有两种：显式执行 refresh table；或在启动 Spark SQL Shell 时通过 --conf 设置 spark.sql.filesourceTableRelationCacheSize=0 禁用缓存，该配置不能用 set 语句设置。
