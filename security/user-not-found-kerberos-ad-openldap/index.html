Hive/Spark/Yarn: User Not Found 错误和 Kerberos / AD / OpenLDAP 之间的关系与解释

原创付费分类：Security发表于：2023-07-31阅读用时：11 分钟 (约 1718 字)阅读：0

有时候，当你向Spark或Hive提交作业时，可能会遇到如下的错误：

提交作业使用的用户是 example-user-1 ，但是Yarn返回的错误信息是：该用户不存在。类似的问题大多发生在启动了Kerberos的Hadoop集群上，或者集群集成了Windows AD或OpenLDAP后。本文，我们把这个问题梳理清楚并给出解决方法。

ContainerExecutor：DefaultContainerExecutor 和 LinuxContainerExecutor

要了解这个问题的根源，需要先了解一下Yarn的ContainerExecutor。我们知道，在Yarn中，作业会被分布到若干个Yarn的Container中去执行，Yarn对于启动和管理Container进行了抽象，设计了 ContainerExecutor 这个抽象基类 ，并提供了两种不同的实现（可以认为是两种策略或管理方式） ，分别是： DefaultContainerExecutor （DCE） 和 LinuxContainerExecutor（LCE） ，并通过配置项： yarn.nodemanager.container-executor.class 来指定使用哪一种。

  • DefaultContainerExecutor 是默认的ContainerExecutor，如果用户不显式地设定 yarn.nodemanager.container-executor.class ，默认使用的就是它。DefaultContainerExecutor逻辑是很直白的：就是由NodeManager的进程负责启动Container，所以Container进程的User就是NodeManager进程的User，在很多平台上，这个User都是 yarn

  • LinuxContainerExecutor 是一个更为强大的ContainerExecutor，它能更有效地限制一个Container所以使用的资源（即资源隔离做得比较好），它主要利用了Linux Kernel的一个名为 CGroup 的特性（参考 Yarn官方文档 ）。使用LCE启动Container时，容器进程所属用户即可以是NodeManager进程的用户（即 yarn ）也可以是提交任务的用户，取决于用户的配置，具体参考下文的截图。

ContainerExecutor 和 Hadoop身份认证 之间的关系

ContainerExecutor（yarn.nodemanager.container-executor.class）和 Hadoop身份认证（hadoop.security.authentication）之间的关系是有一定的耦合关系的：

  • 当Hadoop集群是“非安全模式”（nonsecure-mode）时，ContainerExecutor既可以是DefaultContainerExecutor 也可以是LinuxContainerExecutor，取决于用户配置

  • 当Hadoop集群是“安全模式”（secure-mode）时，ContainerExecutor只能是LinuxContainerExecutor
